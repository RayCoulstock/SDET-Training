# Activity 1 — Trainer Solution: Follow the NeuroPulse Request

## Example trace

With the Participants search changed to `Sarah`, the final request should resemble:

```http
GET /api/participants?search=Sarah HTTP/1.1
Accept: */*
```

The successful response is `200 OK`, has a JSON content type, and its body is an
array. In Normal seed data, one member has `firstName: "Sarah"`, `lastName:
"Miller"`, and an email ending in `@example.test`. The page combines the two name
fields into the link text `Sarah Miller` and shows the email in the adjacent cell.

The strongest link between request and result is not merely the URL: select the
entry whose encoded `search` value equals the final input, inspect its response,
and match a returned identity/name to the rendered row. Earlier requests can finish
out of order while typing.

## Classification

| Observation | Classification | Reason |
| --- | --- | --- |
| `GET`, URL, query encoding, `200`, and content type | Transport | They describe the HTTP exchange. |
| Top-level array and participant field names/types | Representation | They describe the JSON contract. |
| Only participants whose name or email contains the term are returned | Business behaviour | This is the filter outcome a caller needs. |
| The matching name appears as a usable participant link | Business/UI behaviour | Rendering and navigation are browser responsibilities. |

Headers generated by the browser, connection details, and exact timing are useful
diagnostically but are not automatically stable requirements.

## Complementary checks

- **API:** request `/api/participants?search=Sarah` and assert `200`, a JSON array,
  at least one matching result, and no returned name/email that violates the agreed
  matching rule. This isolates server filtering and representation.
- **UI:** enter `Sarah` through the labelled search control, then assert Sarah Miller
  is visible and a known non-match is absent. This proves browser wiring, rendering,
  and the user-facing control rather than rechecking every API field.

A `200` with an empty, unfiltered, or wrongly shaped body is still incorrect. If the
page is empty, compare the final request, response body, console, and render state:
network evidence can separate no server match from a client rendering fault.

## Stretch: status

Selecting Active adds `status=Active`. The response remains an array, but every
member should have `status: "Active"`. Avoid asserting the exact count because seed
state can have been changed by another activity.
